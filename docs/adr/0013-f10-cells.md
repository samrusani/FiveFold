# 0013: F10's delayed and stale-beyond-L cells

Status: Accepted (2026-11-15)
Date: 2026-11-15
Spec sections affected: Fault catalog (the F10 row, through record 0006)

## Context

Record 0006 pairs F10 with F2 at C1, so that G2 probes the destination's status. It fixes one G2 outcome for F10, "F2 with F10 stale beyond L, at C1: fail (5)", and expects every other G2 cell to pass. It also says: "If that run contradicts a claim here, the claim is revisited by decision record. Nobody edits an expectation to match a result."

The first deterministic runs (dev-001, seed 7) contradict two of F10's three cells. The third, stale within L, passes as expected. In all three, the order commits as PO-0001 at virtual time 4,815 ms, F2 drops its answer, and G2 moves the action to OutcomeUnknown at 6,788 ms.

**Delayed: pass_unresolved, where 0006 expects a pass.** F10 delays the next `count` status answers past T. The catalog's default `count` is 20, and record 0005 sets `max_probes` at C1 to 20. So no probe is ever answered in time.

- G2 sent 20 probes, from 7,788 to 64,788 ms. Every answer listed PO-0001, and every one arrived after T and was dropped (`caller_timed_out`).
- G2 escalated at 66,788 ms. dev-001 has no resolver, so the report said `unknown`.

**Stale beyond L: pass, where 0006 expects fail (5).** 0006 says the answers "reflect the state when F10 fired", and F10 fires at `sim.status.answer`. With F2, the first status query comes after the order committed: G2 probes only because F2 dropped the committed answer. So the frozen state already lists the order.

- F10 fired at the first status answer, at 7,834 ms. The answer listed PO-0001.
- G2 confirmed the order at 7,851 ms, and the report said `done`.

0006's narrative ("The stale status made Failed wrong") needs status answers that omit an order that has committed. That cannot happen while the stale state is taken at a status answer.

## Decision

1. **The delayed cell sets `count` to 5**, below `max_probes`. The catalog's default stays 20. The first five probes go unanswered, the sixth is answered in time, and G2 confirms the order. The cell then tests what the variant is for: a late status answer counts as unanswered, and G2 keeps probing. 0006 already sets a cell parameter the same way: the stale-within-L cells set `status_lag_ms` to 3,000.
2. **Stale beyond L fires where the write arrives.** The variant's point becomes `sim.write.received`, matching the write it concerns. The next `count` status answers list the effects as they were just before that write arrived, while claiming to be current. "The state when F10 fired" then means what 0006's narrative needs. The delayed and stale-within-L variants keep `sim.status.answer`.

What a run gives under each part, from an experiment on the current code (dev-001, seed 7, G2 at C1 with F2):

- **Part 1:** with `count` 5, G2 confirms PO-0001 at 22,832 ms after five unanswered probes, and the run passes. Any `count` up to 19 passes; 20 or more escalates.
- **Part 2:** with the state frozen as the order arrived, every answer omits PO-0001. At 15,319 ms an empty answer is past the settle time (`as_of_vt >= sent_vt + S`, 0005), and G2 marks the action Failed. The agent reads the quotes and the budget again, finds the budget spent (74,000 of 100,000 minor units committed), places no second order, and reports `not_done` while PO-0001 exists. The run fails property 5 (`not_done_but_committed`), as 0006 claims. 0006's narrative says the agent's second try was rejected; here the scripted policy does not try, because it reads the spent budget first. The verdict and the failing property are the same.

## Alternatives considered

- **Delayed: keep `count` 20 and list the cell as a documented G2 limit (pass_unresolved).** It is honest, but the cell would only show escalation, which F2 at C0 already shows, and never that G2 recovers after late answers.
- **Delayed: change the catalog's default `count` to 5.** Simpler, but stale beyond L needs a `count` that lasts until the settle time passes (8 answers in this run). One default cannot serve both variants.
- **Stale beyond L: keep the point and freeze the state at an earlier virtual time,** for example `stale_by_ms` before each answer. Whether the order is omitted then depends on probe timing: in the experiment, the first answer that could move the action to Failed was produced at about 15,300 ms, so `stale_by_ms` would need to exceed about 10,500 ms. Fragile.
- **Stale beyond L: record the observed pass and drop 0006's claim.** No cell would then show that G2 trusts the status contract, and that a destination which breaks it can make G2 wrong. Rejected.

## Consequences

- Part 1 changes only the cell's plan (`src/fivefold/harness/cells.py`).
- Part 2 adds `sim.write.received` as F10's point for the stale-beyond-L variant: the fault point code (`src/fivefold/harness/sim_points.py`), the catalog, the plan check and the cell's plan.
- Both cells go into `faults/expected.yaml`: delayed with `count` 5 passes, and stale beyond L fails property 5. Until this record is decided, they stay out, and whole-run tests in `tests/pg/test_delivery_faults.py` pin what the runs do now.
