# 0012: Viewer v1 tooling

Status: Proposed
Date: 2026-11-15
Spec sections affected: Stack (the Viewer row), Architecture (the Viewer component), Repo layout (`viewer/`), Testing

## Context

The spec says the viewer is "React and TypeScript over a read-only API", with its tooling decided at M3 (spec, Stack; 0007, which leaves the viewer to "its own decision record at M3"). Milestone M3 includes viewer v1 (plan).

What the viewer must show, from the product and the records:

- A run's timeline: every message on every hop with its fate, the faults that fired, the scripted humans' actions, the gateway's action events and the final report (0004, 0006, 0009). The demos walk through B0 and G2 side by side on the same seed, about three minutes each (product). "The viewer shows the agent's view beside the ledger" (product, demo 1).
- The five-property scorecard of each run, with reason codes and excused intents, from the `eval` schema (0004).
- A run list. Each run has its own database, and "a small registry database lists runs for the viewer" (0009).
- It is read-only. Its role, `ff_viewer`, can only select from `sim`, `gw`, `harness` and `eval` (0008).

What the repository has today: Python 3.12 with uv, Ruff, mypy and pytest (0007); no JavaScript toolchain. Starlette (1.10.0) and uvicorn (0.54.0) are already installed, as dependencies of the MCP SDK. The spec names FastAPI for the gateway's admin API, which is not built yet.

## Decision (proposed)

1. **Read-only API in Python**, in `src/fivefold/viewer/`, served by Starlette and uvicorn, which the project already installs through the MCP SDK; they become direct dependencies, pinned in `uv.lock`. It connects as `ff_viewer` and has no write path. Endpoints, all `GET`, returning JSON: the run list, one run's summary and scorecard, its timeline (the merged, seq-ordered events of the harness logs and the gateway's action events), and its ledger and fact history.
2. **A run registry**, as 0009 describes: a small database, `fivefold_registry`, with one row per run database (run id, database name, scenario, configuration, contract, seed, created). The harness writes a row when it creates a run database; the API reads it.
3. **Frontend in `viewer/`**: React with TypeScript, built with Vite, tested with Vitest, linted with ESLint, with npm and a committed `package-lock.json` on the current Node LTS. Exact versions are checked and pinned when this record is accepted. The build output is static files that the API serves; there is no server-side rendering.
4. **v1 scope**: the run list; a run page with the timeline, filterable by hop, and the scorecard; and a side-by-side view of two runs of one demo (B0 and G2), aligned by virtual time.
5. **CI**: a separate job builds and tests the viewer, so the Python suite never needs Node. Docker Compose gains a `viewer` service.

## Alternatives considered

- **FastAPI for the viewer API**, as for the admin API in the spec. It would add FastAPI as a new dependency for a handful of read-only endpoints. Starlette, which FastAPI builds on, is already installed. Either fits; Starlette is proposed because it adds nothing new.
- **Server-rendered HTML from Python, with no JavaScript toolchain.** Fewer tools to maintain, but it is not the React and TypeScript viewer the spec fixes, and interactive alignment of two runs is harder. Kept as a fallback if the maintainer prefers one toolchain.
- **A static HTML report per run, generated by a command.** The cheapest, and good for attaching to the published report. It can come later as an export of the same API data.
- **Dashboard frameworks (for example Streamlit).** Fast to start, but not React, hard to test, and they pull in large dependency trees. Rejected.

## Consequences

- A second toolchain (Node, npm) enters the repository, confined to `viewer/` and its CI job.
- The harness gains the registry write; the evaluator and the gateway are unchanged.
- Tests: API tests against migrated run databases (pytest), component tests (Vitest), and one end-to-end check that the API serves a demo run's timeline and scorecard.

## Spec changes on acceptance

- Stack table, Viewer row: "React and TypeScript (Vite, Vitest, ESLint, npm) over a read-only Starlette API; see 0012".
- 0007, Tooling table, Viewer row: "see 0012".
- Repo layout: `viewer/` holds the frontend; `src/fivefold/viewer/` holds the API.
